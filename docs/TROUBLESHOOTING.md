## Первичная проверка

```bash
sudo systemctl status megapbx-max --no-pager
sudo journalctl -u megapbx-max --since "15 minutes ago" --no-pager
curl -fsS http://127.0.0.1:8000/healthz
curl -fsS http://127.0.0.1:8000/readyz
curl -fsS https://bot.example.com/readyz
```

`healthz` подтверждает работу процесса, `readyz` — доступность локального
состояния. Эти ответы не проверяют токен MAX, права в чате и настройки АТС.
Для MAX используйте `check` и `subscriptions` с [загруженным окружением](CONFIGURATION.md#cli-с-production-environment-file).

## Webhook MegaPBX

| Наблюдение | Что проверить |
|---|---|
| `401 Bad CRM token` | Совпадение CRM-ключа с `MEGAPBX_CRM_TOKEN`, способ передачи, рестарт после изменения env |
| Ключ только в `?token=...` | Включён ли `MEGAPBX_ALLOW_QUERY_TOKEN=1`; исключена ли query string из логов каждого прокси |
| `400 Invalid webhook payload` | Валидность JSON или form; при `Content-Type: application/json` form-fallback не применяется |
| `413` | Лимит body и в Nginx, и в переменных `*_WEBHOOK_BODY_BYTES` |
| `503` при постановке в очередь | Доступность SQLite, свободное место, права сервисного пользователя |
| Браузер показывает `403`/`405` | Браузер делает GET, а webhook принимает POST; Nginx может запрещать другие методы |
| `200`, сообщения нет | Фильтр группы/DID, тип и статус звонка, дедупликация, очередь и доставка MAX |
| Нет строки `webhook received` | Проверить DNS, proxy, авторизацию и body: эта строка пишется **после** auth/parse |

Отсутствие строки в application-логе не доказывает, что АТС не отправляла запрос:
он мог завершиться `401` или `400` раньше. Установщик отключает access log
webhook-маршрутов для защиты секретов.

### Проверка маршрута без уведомления

Отправьте POST с правильной авторизацией и заведомо невалидным JSON `{`.
Пример в [README](../README.md#health-checks-и-диагностика). Ожидается `400`:
авторизация пройдена, задание не создано. Не используйте реальные тестовые
`history/Missed` в рабочем чате для проверки доступности.

### События и фильтры

Уведомление создаётся для входящего пропущенного звонка. Фильтруется группа
или DID назначения, а не телефон клиента. Если payload не совпал с фильтром,
HTTP `200` всё равно возможен — это подтверждение приёма, а не отправки MAX.

`ACCEPTED`/`COMPLETED` могут прийти раньше истории или относиться к исходящему
звонку с другим `callid`. Пока направление неизвестно, допустим временный
`event_not_ready`. Когда в inbox есть `OUTGOING` или `history/type=out`
с тем же ID, промежуточные события завершаются без редактирования сообщения.
Автозакрытие исходящего перезвона требует `history/Success/out/missedStatus=2`.
Непустой неизвестный ID промежуточного события не сопоставляется с чужим
уведомлением только по телефону.

## MAX

| Наблюдение | Что проверить |
|---|---|
| API `401` | Токен нужного бота, `Authorization` без `Bearer` |
| API `403` | Членство бота в чате, права администратора, `write` и `read_all_messages` |
| Подписка есть, кнопка не действует | URL `/max/webhook`, тип `message_callback`, совпадение `X-Max-Bot-Api-Secret` |
| Polling конфликтует с Webhook | Использовать один механизм получения обновлений; production-подписку не удалять ради диагностики |
| `429` или временные `5xx` | Backoff/retry, доступность API, состояние очереди |
| `delivery_unknown` / `external_unknown` | Сверить существующее сообщение в MAX; затем применить подходящую reconciliation-команду |

Команды восстановления и их последствия описаны в
[OPERATIONS.md](OPERATIONS.md#8-диагностика). Повтор неизвестной доставки без
сверки может создать дубликат. Нажатие «Я наберу» только отмечает уведомление —
оно не инициирует звонок через АТС.

## DNS, reverse proxy и TLS

Проверьте, что публичный DNS ведёт на HTTPS-прокси, сертификат соответствует
имени, а upstream доступен с хоста прокси. Внутренний DNS может возвращать
другой адрес; проверяйте и из локальной сети, и снаружи.

При внешнем Nginx Proxy Manager типичная схема:

```text
Интернет:443 → NPM с TLS → HTTP:80 на VM → Nginx → 127.0.0.1:8000
```

Ошибка `CERTIFICATE_VERIFY_FAILED` требует проверки времени, полной цепочки
и доверенных корневых сертификатов на машине, выполняющей запрос. Если API
использует ЦС Минцифры, установите проверенный корневой сертификат из официального
источника в системное хранилище Debian/Ubuntu, выполните `update-ca-certificates`
и перезапустите сервис. Installer не скачивает этот сертификат автоматически.
Используйте `SSL_CERT_FILE` для явного bundle; TLS-проверка должна оставаться включённой.

синтетический пример. Уберите токены, номера, имена, реальные ID, URL подписок
